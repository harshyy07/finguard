FinGuard-India
Step-by-Step Implementation Guide
Building an Indian Financial Regulatory Compliance Guard + Chatbot
Purpose. This guide converts the FinGuard research idea into a practical student research project. The recommended implementation is an Indian-regulation, regulation-grounded financial chatbot with query-level and response-level compliance checking. It is designed as an extension/application of the FinGuard paper, not a claim that the original paper itself implemented this exact architecture.
1. What We Are Building
The final system will accept a user's financial question, check whether the request creates a regulatory-compliance risk, retrieve relevant Indian regulatory text when appropriate, generate a response, check that response again, and either show it or replace/block it with a safe response.
Target architecture:
User
  ↓
Query Compliance Guard
  ↓
SAFE ───────────────→ Regulatory Retrieval → LLM → Response Guard → User
  ↓
RISKY → Policy Decision → Safe refusal / compliant alternative → User

3. Phase 1 — Collect Official Regulatory Documents
Goal: create a clean, traceable regulatory source collection.
3.1 Where to obtain documents
SEBI official website: https://www.sebi.gov.in/legal.html
RBI official website: https://www.rbi.org.in/ (add later if the scope expands to banking/payment regulation)

4. Phase 2 — Extract and Clean the Regulations
Goal: convert PDFs into structured text while preserving section/clause boundaries.
Pipeline:
PDF
↓
Text extraction (PyMuPDF)
↓
Remove headers/footers and obvious noise
↓
Preserve headings, sections, clauses, page numbers
↓
Structured JSON
4.1 Suggested JSON format
{  "regulator": "SEBI",  "document": "Document title",  "section": "Section / regulation number",  "page": 12,  "text": "Original clause text...",  "source_url": "https://..."}
4.2 Quality check
Open 5–10 random extracted pages and compare them with the PDF.
Check that section numbers are not lost.
Check that tables and bullet points are not badly merged.
If a PDF is scanned, add OCR rather than trusting empty extracted text.
5. Phase 3 — Extract Compliance Points
A regulation is not yet a training label. Convert each relevant clause into a concise compliance point: what an institution/person must do, must not do, or must disclose.
Example format:
{  "rule_id": "SEBI_001",  "source_section": "...",  "compliance_point": "The regulated entity must ...",  "risk_if_violated": "..."}
At this stage, use an LLM to assist extraction if desired, but keep the original clause beside the generated compliance point and perform human review. The original regulation is the source of truth.
6. Phase 4 — Build the Indian Compliance Taxonomy
Taxonomy means a hierarchy of categories. The goal is to discover a defensible set of Indian financial compliance-risk categories from the regulations rather than inventing labels first.
Recommended pipeline:
Compliance points
↓
Text embeddings
↓
HDBSCAN clustering
↓
Cluster inspection / LLM-assisted summaries
↓
Human review
↓
Final categories + subcategories
6.1 Embeddings
An embedding converts text into a numerical vector that captures semantic information. Similar compliance points tend to have nearby representations. A SentenceTransformers model can be used for the first prototype.
6.2 HDBSCAN
HDBSCAN is a density-based clustering algorithm. It groups points that naturally form dense regions and can leave unusual points as noise. This is useful when you do not know the correct number of categories beforehand.
6.3 Taxonomy output
category_id,category_name,definition,source_rule_idsC01,Example category,"Definition based on reviewed regulations","SEBI_001;SEBI_014"C02,Example category,"Definition based on reviewed regulations","SEBI_008;SEBI_022" 
7. Phase 5 — Create Training and Benchmark Data
Create examples from the taxonomy and source regulations. Keep training and test sources separated to avoid leakage.
7.1 Query types
Clearly compliant questions
Clearly non-compliant requests
Ambiguous questions requiring context
Paraphrases of the same intent
Indirect/obfuscated requests
Benign questions containing compliance-related keywords
Safe educational questions about a regulated topic
7.2 Query + response labels
Label both the user query and the generated response. This matters because a safe question can receive an unsafe answer.
{  "id": "EX_001",  "query": "...",  "query_label": "safe",  "query_category": null,  "response": "...",  "response_label": "unsafe",  "response_category": "C02",  "source_rule_ids": ["SEBI_014"]}
7.3 Human annotation
Use at least two reviewers for a meaningful subset. Record disagreements and resolve them through a documented consensus process. Do not treat an LLM-generated label as ground truth.
8. Phase 6 — Adversarial Augmentation
Create harder versions of existing examples so the detector learns intent rather than memorizing keywords. Examples include paraphrasing, indirect intent, role/context changes, and harmless-looking framing.
Example:
Base intent:"How can I evade a financial reporting requirement?"Harder variants:- indirect wording- hypothetical framing- role-play framing- euphemisms- multi-turn context- benign context followed by a risky request
For safety and evaluation, generate adversarial examples for testing the guard; do not build a dataset whose purpose is to provide real-world evasion instructions.
9. Phase 7 — Build the Regulation Retrieval System (RAG)
Goal: retrieve the most relevant regulatory clauses for a user's question or a detected risk.
Pipeline:
Regulation chunks
↓
SentenceTransformer embeddings
↓
FAISS index
↓
User query embedding
↓
Top-k relevant clauses
↓
LLM receives query + retrieved evidence
9.1 Retrieval record
{  "chunk_id": "SEBI_DOC1_P12_C4",  "score": 0.82,  "regulator": "SEBI",  "section": "...",  "text": "...",  "source_url": "..."}
Keep the source identifier with every retrieved chunk so the final UI can show where the regulatory evidence came from.
10. Phase 8 — Implement the Compliance Guard
Start with a simple baseline before fine-tuning. The baseline can be a prompted open-weight LLM classifier. Later, fine-tune a smaller model with your labeled dataset.
Target classifier output:
{  "label": "unsafe",  "category": "C02",  "confidence": 0.91}
The exact JSON format is your application design; it is not required to match the FinGuard paper's internal implementation.
11. Phase 9 — Implement the Two-Checkpoint Chatbot
Recommended production-style flow:
1. User submits a question.
2. Query Guard classifies it.
3. If clearly risky, do not send it to the normal answer-generation path; route to a safe-response policy.
4. If allowed, retrieve relevant regulatory context.
5. Send the question + relevant evidence + response policy to the LLM.
6. Run the generated response through the Response Guard.
7. If compliant, show it.
8. If risky, discard/regenerate or return a safe alternative.
11.1 Pseudocode
def handle_query(user_query):    query_result = guard.check(user_query)    if query_result.is_unsafe:        return safe_response(            reason=query_result.category        )    evidence = retriever.search(user_query, top_k=5)    draft = llm.generate(        query=user_query,        regulatory_context=evidence    )    response_result = guard.check(        user_query + "\n" + draft    )    if response_result.is_unsafe:        return safe_response(            reason=response_result.category,            evidence=evidence        )    return draft
12. Phase 10 — Safe Response / Policy Layer
The detector tells the application that a risk exists. A separate policy layer decides what the chatbot should do.
Detection result
Policy action
User-facing behavior
Safe
Allow
Answer normally, grounded in retrieved sources where relevant.
Risky but answerable safely
Constrain
Give a compliant explanation without facilitating the risky action.
Clearly evasion/fraud assistance
Refuse
Refuse the harmful instructions and offer lawful/educational alternatives.
Uncertain
Escalate/caution
Avoid confident legal claims; provide general information and cite the relevant source.

15. Phase 13 — Establish the Research Baseline
Do not jump directly to the proposed improved system. Build a baseline so you can measure whether the improvement actually helps.
Recommended experimental ladder:
Baseline A: General LLM prompted as a compliance classifier.
Baseline B: Retrieval + prompted LLM classifier.
Baseline C: Fine-tuned compliance guard.
Proposed system: Fine-tuned guard + regulatory retrieval + response guard + your selected research improvement.

20. What NOT to Do
Do not download thousands of PDFs before validating the pipeline.
Do not copy the FinGuard Chinese taxonomy and relabel it as Indian.
Do not use blogs as the primary source of regulatory truth.
Do not let an LLM-generated label become the only ground truth.
Do not evaluate only on questions containing obvious keywords such as 'fraud' or 'AML'.
Do not claim legal certainty from a model prediction.
Do not compare only final chatbot answers; separately evaluate query detection, response detection, retrieval, and end-to-end behavior.
Do not choose the final novelty claim until the baseline and failure analysis are complete.

22. Important Research/Safety Note
This system is a research prototype for regulatory-compliance detection. Financial regulations change, jurisdiction and product context matter, and a model classification is not itself a legal determination. Use current official regulatory sources, retain source/version metadata, and present regulatory evidence with appropriate uncertainty.
